# Domain docs

Potcast uses a single-context layout. Before exploring the codebase, read the root `GLOSSARY.md` and any ADRs in `docs/adr/` relevant to your work. Continue if either is absent. The domain-modeling skill adds these files as terms and decisions are settled.

Use glossary terms in issue titles, design proposals, and tests. If a term is missing, check how the project already names the concept and record any gap for domain modeling.

If a proposal conflicts with an ADR, name the ADR and explain why the decision should be reopened.
